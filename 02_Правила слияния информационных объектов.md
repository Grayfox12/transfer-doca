# Правила слияния информационных объектов

Правила, по которым СПО на каждом узле применяют межузловые события об информационных объектах: версии и их генерация, слияние целиком и по полям, удаление, повторная синхронизация, поля в теле сообщения и заголовки. Правила реализует пакет правил слияния на Python (владелец — 554); СПО передаёт ему хранение объектов и функцию проверки итога. Решения — [ADR-0092](../90_ADR/ADR-0092%20Тиражирование%20данных%20между%20узлами%20—%20перечень%20топиков,%20полное%20состояние,%20слияние,%20повторная%20синхронизация.md) и [ADR-0093](../90_ADR/ADR-0093%20Слияние%20по%20полям%20—%20метки%20единиц%20слияния%20в%20jsonb,%20описание%20в%20опциях%20proto.md). Детали, помеченные «предложение агента», подтверждены архитектором 2026-11-13.

## 1. Общие правила

- Межузловое событие несёт **полное состояние** объекта; ключ сообщения — идентификатор объекта (ADR-0092, Р2).
- С узла уходят только топики из **перечня межузловых топиков**; остальные — для служебного пользования узла (ADR-0092, Р1).
- Объект, полученный с другого узла, хранит тот же СПО на узле-получателе, с пометкой узла. По умолчанию объект может менять СПО-владелец на любом узле; ПК КНСИ и ПК ФХ изменять чужие объекты запрещено; остальные изделия решают при разработке (ADR-0092, Р3).
- **Домашний узел** — узел, где объект создан; записывается в объект при создании и не меняется. Ручной конфликт решает домашний узел (ADR-0092, Р3б).
- Для сравнения версий **заголовки не используются**: все поля версии — у объекта в базе и в теле сообщения.
- Итог слияния **не зависит от порядка** прихода событий: при одинаковом наборе событий все узлы приходят к одному итогу.
- У объекта в системе всегда **одна схема**; смена опций `sync.*` — несовместимое изменение схемы (ADR-0093).

## 2. Что задаётся при разработке объекта

Для каждого межузлового информационного объекта — опциями Protobuf в схеме `.proto` в общем репозитории схем (ADR-0093):

| Опция | Где | Значения | По умолчанию |
|---|---|---|---|
| `(sync.mode)` | сообщение | `A` — побеждает последнее изменение (HLC); `B` — явный конфликт (векторная версия) | `A` |
| `(sync.merge)` | сообщение | `WHOLE` — целиком; `FIELDS` — по полям | `WHOLE` |
| `(sync.group)` | поле | имя группы: поля группы сливаются как одно — так задаются поля, которые нельзя менять порознь | — |
| `(sync.list_key)` | поле `repeated` | имя поля-идентификатора элемента: слияние по элементам | — |
| `(sync.list_set)` | поле `repeated` | слияние как множество | — |

Смену опций `sync.*` у существующего сообщения ловит отдельная проверка в общем репозитории схем: `buf breaking` её не замечает.

## 3. Версия и её генерация

### 3.1. Режим «а» — гибридные логические часы (HLC)

Метка HLC — пара `(wall_ms, counter)`: физическое время в миллисекундах и счётчик. У СПО на узле **одна** последняя выданная метка `last` на все экземпляры СПО; она читается и обновляется атомарно в той же транзакции, что изменение объекта (например, строка в служебной таблице с блокировкой). Иначе два экземпляра выдадут одинаковые метки, и вторую правку получатели отбросят как дубль.

Генерация (стандартный алгоритм HLC):
1. **Изменение на своём узле:** `wall = max(last.wall_ms, now)`; если `wall == last.wall_ms` — `counter = last.counter + 1`, иначе `counter = 0`. Метка — `(wall, counter)`; `last` обновляется ею в той же транзакции.
2. **Получение события с меткой `m`** (после применения, в той же транзакции): `wall = max(last.wall_ms, m.wall_ms, now)`; `counter` — `max(last.counter, m.counter) + 1`, если `wall` равен обоим; `last.counter + 1`, если равен только `last.wall_ms`; `m.counter + 1`, если равен только `m.wall_ms`; иначе `0`. Так следующее изменение на узле получит метку больше всего, что узел видел.
3. **Убежавшие часы:** если `m.wall_ms > now + порог` — событие всё равно применяется (иначе узлы разойдутся), но СПО шлёт оповещение в ПК УФ; порог — TBD.

Сравнение: больше `(wall_ms, counter)`; при равенстве — больше псевдоним узла изменения (строковое сравнение).

После исследований и тестов возможен переход к приоритету домашнего узла поверх HLC (ADR-0092).

### 3.2. Режим «б» — векторная версия

Вектор `{узел: счётчик}`, например `{"uovu": 3, "covu": 1}`; узла нет в векторе — его счётчик 0.
1. **Изменение на своём узле:** счётчик своего узла +1.
2. **Сравнение:** вектор A новее B, если по всем узлам не меньше и хотя бы по одному больше; равны — дубль; иначе — **несравнимы**.
3. **Слияние:** по каждому узлу — максимум.
4. **Итог ручного конфликта** публикует домашний узел: слияние векторов обеих спорных версий плюс 1 своему узлу.

### 3.3. Когда меняется версия

- Версия и метки единиц меняются в одной транзакции с изменением объекта и строкой outbox ([ADR-0007](../90_ADR/ADR-0007%20Публикация%20событий%20СПО%20—%20outbox,%20CDC%20или%20публикатор.md)).
- Объект **целиком**: получатель применяет событие, только если его версия новее версии объекта у себя; равная — дубль; в режиме «б» несравнимая — конфликт (ADR-0092).
- Объект **по полям**: событие всегда идёт в слияние по единицам; проверки на дубль нет — повторное слияние ничего не меняет. Версия объекта после слияния — максимум меток единиц (режим «а») или слияние векторов (режим «б») (ADR-0093 частично заменяет здесь ADR-0092).

## 4. Слияние

### 4.1. Алгоритм

![Алгоритм применения межузлового события об объекте](../_assets/scheme_13.svg)

Описание схемы:
1. Событие об объекте читается из внутреннего топика; топики объекта опрашиваются по порядку `created` → `updated` → `deleted`.
2. Объекта у себя нет — создать из события (полное состояние) и перейти к сохранению. Как поступать с `updated`, пришедшим раньше `created`, — по тестам (Q-089).
3. Способ слияния по `(sync.merge)`: целиком (п. 4–6) или по полям (п. 7–11).
4. Целиком: версия события равна версии объекта у себя — точный дубль, пропустить.
5. Целиком, режим «а»: побеждает большая метка HLC, при равенстве — псевдоним узла; проигравшая версия — в журнал отброшенных правок (§4.5).
6. Целиком, режим «б»: вектор события новее — применить; старее — пропустить; несравнимы — объект «в конфликте», обе версии хранятся.
7. По полям: проверки на дубль нет; каждая единица слияния (§4.2) сливается отдельно: значения множества — по п. 10, остальные единицы — по режиму (п. 8–9).
8. По полям, режим «а»: значение с большей меткой HLC единицы; перезаписанное значение — в журнал отброшенных правок. Удаление решает метка `flag_actual_action`, правка удалённый объект не возвращает (§5).
9. По полям, режим «б»: от каждой стороны остаются версии, которые другая сторона не видела (метку не покрывает вектор её объекта); одна версия — берётся она; несколько — конфликт по единице, набор спорных версий хранится и передаётся. У `flag_actual_action` и элемента списка по ключу правка неудалённого объекта даёт версию «жив», поэтому параллельные удаление и правка — конфликт по единице; несколько версий с одним значением (только «жив» или только «удалён») — не конфликт (§5).
10. Значения множества, оба режима: наборы меток добавления объединяются, метка с признаком «удалён» хотя бы у одной стороны — «удалён»; несколько меток — не конфликт (§4.4).
11. Проверка итога функцией СПО, если по объекту нет конфликта; без отката: нарушено — пометка «нарушено правило» (местная, снимается, когда проверка проходит), журнал, оповещение. Пока по объекту есть конфликт, проверка не запускается, а пометка снимается. Автоматически исправляет нарушение только домашний узел — новым изменением; человек — на любом узле, где у него есть права.
12. Сохранить объект, версию и метки в одной транзакции; обновить последнюю метку HLC СПО по правилу получения (§3.1).
13. Есть конфликт — по полям решает только домашний узел (человек или правило СПО); целиком — по ADR-0092, Р3б. Итог — новое изменение единицы или объекта с меткой, которая видела все спорные версии. Другие события конфликт не снимают; на других узлах спорная единица только для чтения, пока конфликт не снят; при конфликте по удалению не правится весь объект или весь элемент списка (§5).

### 4.2. Единицы слияния и их метки

Единица слияния — поле, группа `(sync.group)`, элемент списка по ключу, элемент множества, признак удаления объекта `flag_actual_action`.

У единицы — **набор версий**, у каждой версии своя метка:
- режим «а» — `(hlc_wall_ms, hlc_counter, node)` изменения;
- режим «б» — пара `(node, counter)`: узел изменения и значение его счётчика в векторе объекта сразу после изменения. Метку **покрывает** вектор `V`, если `V[node] >= counter`: сторона с вектором `V` это изменение уже видела.

Обычно версия одна; несколько — при конфликте по единице (режим «б»), у `flag_actual_action` и элемента списка по ключу при параллельных правках (§5) и у значения множества (несколько добавлений, §4.4). Изменение на своём узле даёт единице одну новую версию, она заменяет все прежние, в том числе спорные — только так снимается конфликт по единице, и только на домашнем узле (§4.1, п. 13); на других узлах спорная единица только для чтения, при конфликте по удалению — весь объект или элемент списка (§5). Значения множества так не сливаются — §4.4.

Ключи меток в `field_stamps` (предложение агента):

| Единица | Ключ | Пример |
|---|---|---|
| поле | имя поля | `status` |
| группа | `@` + имя группы | `@coords` |
| элемент списка по ключу | `поле[ключ]` и `поле[ключ].поле_элемента` | `crew[7]`, `crew[7].role` |
| элемент множества | `поле{значение}`, для добавления — со своей меткой | `tags{срочно}` |
| признак удаления | `flag_actual_action` | `flag_actual_action` |

### 4.3. Списки

Список — поле `repeated` или `map`.

| Вид списка | Пример | Способ |
|---|---|---|
| упорядоченный | точки маршрута, этапы плана | **целиком** (обязательно): одна единица слияния; в режиме «б» параллельная правка — конфликт |
| подобъекты с идентификатором внутри объекта | состав расчёта `{id, ФИО, роль}` | **по элементам с ключом** `(sync.list_key)`: единицы — элемент (значения «жив» и «удалён») и его поля; удаление элемента и параллельная правка его поля — по правилу удаления объекта (§5) |
| `map` | атрибуты «ключ → значение» | по элементам без опции: элемент — одна единица, полей-единиц у него нет, ключ — ключ `map`; удаление — версия элемента с признаком «удалён», сливается как любая единица |
| значения без идентификатора | телефоны, теги | **как множество** `(sync.list_set)`, §4.4 |
| ссылки на другие информационные объекты | приданные подразделения | **как множество**; связанные объекты сливаются отдельно, по своим версиям |
| — по умолчанию | | **целиком** |

Подобъект со своим топиком и версией — отдельный информационный объект, а не список.

### 4.4. Множества

- Работает одинаково в режимах «а» и «б»; общие правила единиц (новая версия заменяет прежние, несколько версий — конфликт) к значениям множества не применяются (ADR-0093, п. 8).
- Каждое добавление значения получает свою метку; одно значение может иметь несколько меток добавления (добавили на разных узлах) — они хранятся набором версий единицы `поле{значение}`. Добавление — новая метка в набор, прежние не заменяются.
- Удаление значения ставит признак «удалён» у всех меток добавления, которые удаляющий узел видит; метки хранятся с этим признаком.
- Слияние: наборы меток двух сторон объединяются; если одна и та же метка хотя бы у одной стороны с признаком «удалён», итог — «удалён». Несколько меток у значения — не конфликт.
- Значение есть в множестве, если у него есть хотя бы одна метка без признака «удалён». Поэтому параллельные «добавил» и «удалил» — **побеждает добавление** (OR-Set, ADR-0093); повторное добавление после удаления — новая метка, значение возвращается.

### 4.5. Журнал отброшенных правок

Пишет СПО в режиме «а» (предложение агента по составу):
- **целиком** — когда версия объекта проиграла: идентификатор и тип объекта; победившая версия — метка и узел; отброшенная версия — метка, узел и полное состояние; время записи; `x-message-id` отброшенного события;
- **по полям** — когда значение единицы перезаписано (ADR-0093): идентификатор и тип объекта; единица; перезаписанное значение; метки и узлы проигравшей и победившей версий; время записи; `x-message-id` события.

Где хранится и сколько — Q-091.

## 5. Удаление

- Удаление **мягкое**: выставляет атрибут `flag_actual_action`, запись остаётся в базе. Удаление — такое же изменение с версией.
- По полям `flag_actual_action` — отдельная единица слияния со значениями «жив» и «удалён» (ADR-0093, п. 9):
  - режим «а» — решает её метка; правка поля удалённый объект не возвращает;
  - режим «б» — любое изменение объекта, не удалённого на своём узле, даёт `flag_actual_action` новую версию «жив» с меткой этого изменения; изменение уже удалённого у себя объекта её не меняет. Поэтому удаление и правка, которые не видели друг друга, — версии «удалён» и «жив» одной единицы, конфликт по единице: он хранится, передаётся в событии и не зависит от порядка событий. Несколько версий с одним значением (только «жив» или только «удалён») — не конфликт. Правка, сделанная после того, как удаление видели, объект не возвращает;
  - объект в конфликте по удалению не правится, пока конфликт не снят, — ни на одном узле: на домашнем узле его снимает явное решение — восстановить или удалить повторно; на других узлах объект только для чтения;
  - вернуть удалённый объект — только явным восстановлением: снятием `flag_actual_action`.
- То же правило — для элемента списка по ключу: правка поля элемента, не удалённого у себя, даёт единице элемента `поле[ключ]` версию «жив»; удаление элемента и параллельная правка его поля — конфликт по единице элемента; элемент в таком конфликте не правится, как объект. Элемент `map` — одна единица, его удаление и правка сливаются как версии этой единицы (§4.3).
- Пример (режим «б»): исходно у всех `{h:1}`. X удаляет объект — `flag_actual_action` = «удалён» `(x,1)`. Y параллельно правит `u` — `u` = `(y,1)`, `flag_actual_action` = «жив» `(y,1)`. На любом узле, получившем оба изменения в любом порядке и любыми событиями, у `flag_actual_action` две версии — конфликт.
- Потребители СПО опрашивают топики объекта по порядку: `created`, потом `updated`, потом `deleted` ([BL-080](../80_Базис/BL-080%20Именование%20топиков%20СПО%20—%20name_spo.name_io.action.md)).
- `updated`, пришедший раньше `created`, в том числе `updated` подобъекта без созданного объекта, — как обрабатывать, определить по результатам тестов.
- Срок хранения записей, помеченных удалёнными, — Q-087.

## 6. Повторная синхронизация узла

По ADR-0092, Р4:
1. Полную отправку по запросу администратора делают только узлы, которым правила ADR-0027 разрешают слать данные восстанавливаемому узлу.
2. Каждый СПО отправляет полное состояние объектов, у которых его узел домашний, включая помеченные удалёнными, с `x-targets` на восстанавливаемый узел.
3. У отправки есть номер `resync_id`, он — в теле каждого объекта. Отправку обрамляют маркеры `ResyncBegin` и `ResyncEnd` — отдельные типы сообщений Protobuf; `ResyncEnd` несёт `resync_id` и число объектов по каждому топику. В какой топик пишутся маркеры — TBD.
4. Получатель сверяет, только когда получил столько объектов, сколько указано в `ResyncEnd`: объекты домашнего узла-отправителя, которых не было в отправке и у которых нет местных неотправленных изменений, помечаются удалёнными.
5. Запасной путь — перенос на носителе, затем догон через ПК ШД.

|---|---|---|---|
| `home_node` | `string` | домашний узел, псевдоним по [BL-082](../80_Базис/BL-082%20Псевдоним%20узла%20—%20snake_case%20без%20точек.md) | все |
| `changed_node` | `string` | узел последнего изменения | все |
| `hlc_wall_ms` | `int64` | метка HLC объекта: время | «а» |
| `hlc_counter` | `uint32` | метка HLC объекта: счётчик | «а» |
| `version_vector` | `map<string, uint64>` | векторная версия | «б» |
| `field_stamps` | `map<string, FieldVersions>` | набор версий каждой единицы слияния, ключи — §4.2 | `FIELDS` |
| `resync_id` | `string` | номер полной отправки; пусто вне отправки | все |

`FieldVersions`: `repeated FieldStamp versions` — обычно одна версия; несколько — при конфликте по единице и у значения множества. `FieldStamp`: `node`; `hlc_wall_ms`, `hlc_counter` (режим «а») или `counter` (режим «б»); `deleted` — для элементов списков, `map` и меток множеств; `value` — значение спорной версии при конфликте по единице (тип — TBD при реализации пакета).

Атрибут удаления — `flag_actual_action` (со слов архитектора); как он передаётся в теле — TBD.

В базе СПО: те же поля в таблице объекта; `field_stamps` — колонка jsonb ([BL-015](../80_Базис/BL-015%20Основная%20СУБД%20—%20PostgreSQL%2015%20и%20PostGIS.md), ADR-0093).

## 8. Заголовки

Заголовки нужны для доставки и трассировки, для сравнения версий не используются.

| Заголовок | Смысл | Ставит | Решение |
|---|---|---|---|
| `x-origin` | узел, где возникло событие | источник: служебный пакет из `AUTOMATIZATION_NODE_NAME` или CDC (`InsertHeader`); нет — Outgoing | [BL-085](../80_Базис/BL-085%20x-origin%20—%20узел,%20где%20возникло%20событие.md), [ADR-0024](../90_ADR/ADR-0024%20x-origin%20и%20x-message-id%20—%20ставит%20источник,%20Outgoing%20страхует.md), [ADR-0091](../90_ADR/ADR-0091%20x-origin%20при%20CDC%20—%20псевдоним%20из%20AUTOMATIZATION_NODE_NAME%20через%20EnvVarConfigProvider.md) |
| `x-home` | домашний узел объекта; только у событий об объекте; по нему определяются данные РАЙОНА ([BL-087](../80_Базис/BL-087%20Данные%20РАЙОНА%20поднимаются%20вверх,%20справочники%20—%20всем.md)) | источник: служебный пакет (значение из объекта) или колонка `home` в outbox | ADR-0092, Р3в |
| `x-message-id` | глобальный идентификатор сообщения для дедупликации | источник; нет — Outgoing | ADR-0024 |
| `x-schema` | полное имя типа Protobuf `<package>.<Message>` | источник | [ADR-0022](../90_ADR/ADR-0022%20Схемы%20Protobuf,%20версионирование%20и%20заголовки%20сообщений.md), [ADR-0028](../90_ADR/ADR-0028%20Заголовки%20x-schema,%20x-event-time,%20traceparent%20при%20CDC.md) |
| `x-event-time` | время события у источника | источник | ADR-0022, ADR-0028 |
| `traceparent` | контекст трассировки | источник | ADR-0028 |
| `x-targets` | целевые узлы, сужает цели правил | источник: служебный пакет или колонка `targets` в outbox | [ADR-0027](../90_ADR/ADR-0027%20Маршрутизация%20межузлового%20обмена%20—%20редакция%20по%20ревью.md) |
| `x-visited` | посещённые узлы | Outgoing, Ingoing | ADR-0027 |
| `x-source-raw-topic` | исходный внутренний топик | Outgoing | ADR-0027 |

Новых заголовков сверх `x-home` нет.
