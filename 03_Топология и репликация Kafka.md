# Топология и репликация Kafka

Схема распространения событий между узлами через Kafka. У каждого узла свой кластер Kafka. Обмен между узлами идёт через **MirrorMaker 2** и приложения **Kafka Streams**, которые рассылают сообщения по узлам, отсекают дубли и перекладывают входящее во внутренние топики. Решение — [ADR-0027](../../90_ADR/ADR-0027%20Маршрутизация%20межузлового%20обмена%20—%20редакция%20по%20ревью.md) (заменил ADR-0016, который заменил BL-045), MM2 на узле-получателе — [ADR-0018](../../90_ADR/ADR-0018%20Раздельные%20кластеры%20Kafka%20Connect%20для%20MM2%20и%20Debezium.md).

## 1. Общая концепция

Каждый узел n содержит:
- **Внутренние топики** `name_spo.name_io.action` ([BL-080](../../80_Базис/BL-080%20Именование%20топиков%20СПО%20—%20name_spo.name_io.action.md)) — события, возникшие на узле.
- **Outgoing Kafka Streams** — читает внутренние топики и `pk_shd.transit`, определяет цели по правилам маршрутизации и пишет сообщение в исходящий топик `sync.n.<следующий узел>` (раздел 5.1).
- **MirrorMaker 2** — коннектор `MirrorSourceConnector` в отдельном кластере Kafka Connect MM2 узла ([ADR-0018](../../90_ADR/ADR-0018%20Раздельные%20кластеры%20Kafka%20Connect%20для%20MM2%20и%20Debezium.md)): по одному на каждый узел-источник. Коннектор на узле X забирает `sync.n.X` из кластера узла n через VPN и пишет в свой кластер под тем же именем.
- **Ingoing Kafka Streams** — читает входящие топики `sync.*.n`, отсекает дубли, добавляет узел в `x-visited`; нужное узлу пишет во внутренний топик, транзит — в `pk_shd.transit`.

Сообщение доходит до целевых узлов без зацикливания (`x-visited`), дубли отсекаются по глобальному идентификатору.

## 3. Компоненты и их функции

### 3.1. Топики

| Топик | Где | Кто пишет | Кто читает |
|---|---|---|---|
| `name_spo.name_io.action` | узел n | СПО (через outbox и CDC или публикатор, [ADR-0007](../../90_ADR/ADR-0007%20Публикация%20событий%20СПО%20—%20outbox,%20CDC%20или%20публикатор.md)), Ingoing | Outgoing, потребители узла |
| `sync.n.X` | узел n и узел X (имя одинаковое); заводится, только если с n нужно передавать на X; срок хранения на n — предельная автономность × 3 (сейчас 90 дней), на X — 3 дня (ADR-0021) | на n — Outgoing; на X — MM2 | на n — MM2 узла X; на X — Ingoing |
| `pk_shd.transit` | узел n | Ingoing — транзит, не нужный узлу | Outgoing |
| `name_spo.name_io.dlq`, `pk_shd.node.dlq` | узел n; служебные топики ПК ШД, шаблон BL-080 не распространяется | Outgoing, Ingoing — сбойные сообщения (общий — когда объект не определить) | разбор вручную ([ADR-0021](../../90_ADR/ADR-0021%20Гарантии%20доставки%20межузлового%20обмена,%20сроки%20хранения%20и%20DLQ.md)) |

Шаблон внешнего топика — `sync.<откуда>.<куда>`. Псевдоним узла — snake_case без точек ([BL-082](../../80_Базис/BL-082%20Псевдоним%20узла%20—%20snake_case%20без%20точек.md)).

### 3.2. Outgoing Kafka Streams

Работает на каждом узле:
- читает внутренние топики и `pk_shd.transit`;
- если заголовка `x-visited` нет, создаёт пустой массив;
- определяет цели и следующий узел для каждой цели (раздел 5.1) и пишет сообщение в `sync.n.<следующий узел>`, добавляя:
  - текущий узел в `x-visited`;
  - `x-source-raw-topic` — исходный внутренний топик;
- если нет `x-origin` или `x-message-id`, ставит их сам: свой узел и `<узел>:<топик>:<партиция>:<смещение>` ([ADR-0024](../../90_ADR/ADR-0024%20x-origin%20и%20x-message-id%20—%20ставит%20источник,%20Outgoing%20страхует.md)).

### 3.3. MirrorMaker 2

- Коннектор `MirrorSourceConnector` в кластере Kafka Connect MM2 узла-получателя — отдельном от Kafka Connect для Debezium ([ADR-0018](../../90_ADR/ADR-0018%20Раздельные%20кластеры%20Kafka%20Connect%20для%20MM2%20и%20Debezium.md)).
- На узле X — по одному коннектору на каждый узел n, с которого X принимает данные; коннектор берёт ровно один топик `sync.n.X`.
- Имя топика не меняется: `IdentityReplicationPolicy` ([ADR-0027](../../90_ADR/ADR-0027%20Маршрутизация%20межузлового%20обмена%20—%20редакция%20по%20ревью.md), перенесено из ADR-0016).
- Параметры для медленных каналов: батчинг (`batch.size`, `linger.ms`), сжатие (`compression.type`), увеличенные таймауты (`request.timeout.ms`, `delivery.timeout.ms`), ограничение скорости (если поддерживается).

### 3.4. Ingoing Kafka Streams

Работает на каждом узле:
- читает все входящие топики `sync.*.n`;
- извлекает глобальный уникальный идентификатор сообщения из `x-message-id` ([ADR-0024](../../90_ADR/ADR-0024%20x-origin%20и%20x-message-id%20—%20ставит%20источник,%20Outgoing%20страхует.md));
- проверяет его в базе дедупликации (state store, Q-019): есть — пропускает, нет — сохраняет;
- добавляет текущий узел в `x-visited`, если его там нет;
- если сообщение нужно на этом узле, пишет его во внутренний топик по `x-source-raw-topic`;
- если узлу не нужно, но идёт через него дальше, — пишет в `pk_shd.transit` (ADR-0027).

Outgoing и Ingoing — отдельные приложения на Kafka Streams без фреймворка, образы на Debian 12, телеметрия — OTel SDK ([ADR-0017](../../90_ADR/ADR-0017%20Приложения%20Kafka%20Streams%20ПК%20ШД.md)).

## 4. Заголовки сообщений

Тело сообщения — Protobuf ([BL-028](../../80_Базис/BL-028%20Формат%20сообщений%20—%20Protobuf%20и%20заголовки.md)). Свои заголовки — по конвенции `x-*` ([BL-046](../../80_Базис/BL-046%20Конвенция%20заголовков%20Kafka%20—%20x-.md)); она распространяется только на наши внутренние заголовки, которыми мы управляем, `traceparent` — исключение (со слов архитектора, [BL-084](../../80_Базис/BL-084%20Конвенция%20x-%20—%20только%20для%20своих%20заголовков,%20traceparent%20—%20исключение.md)). ПК ШД не производит глубокого логического контроля сообщений: Outgoing и Ingoing работают с заголовками, тело не разбирают. Схемы, версионирование и заголовки — [ADR-0022](../../90_ADR/ADR-0022%20Схемы%20Protobuf,%20версионирование%20и%20заголовки%20сообщений.md).

| Заголовок | Смысл | Ставит | Читает | Статус |
|---|---|---|---|---|
| `x-origin` | Узел, где возникло событие | Источник: внутренний пакет (Python) или CDC (`InsertHeader`); нет — Outgoing ставит свой узел ([ADR-0024](../../90_ADR/ADR-0024%20x-origin%20и%20x-message-id%20—%20ставит%20источник,%20Outgoing%20страхует.md)) | Outgoing — правила маршрутизации; потребители | BL-028, [BL-085](../../80_Базис/BL-085%20x-origin%20—%20узел,%20где%20возникло%20событие.md) |
| `x-visited` | Массив посещённых узлов (JSON) | Outgoing (добавляет свой узел перед отправкой), Ingoing (добавляет свой узел при приёме) | Outgoing — кому не отправлять | BL-028, BL-046, [ADR-0027](../../90_ADR/ADR-0027%20Маршрутизация%20межузлового%20обмена%20—%20редакция%20по%20ревью.md) |
| `x-targets` | Целевые узлы, массив JSON; сужает цели, разрешённые правилами | Источник: внутренний пакет или колонка `targets` в outbox при CDC | Outgoing | [ADR-0027](../../90_ADR/ADR-0027%20Маршрутизация%20межузлового%20обмена%20—%20редакция%20по%20ревью.md) |
| `x-source-raw-topic` | Исходный внутренний топик (`name_spo.name_io.action`) | Outgoing на узле, где событие возникло | Ingoing — в какой внутренний топик писать; при отсутствии — в `pk_shd.node.dlq` | ADR-0027, [ADR-0021](../../90_ADR/ADR-0021%20Гарантии%20доставки%20межузлового%20обмена,%20сроки%20хранения%20и%20DLQ.md) |
| `x-message-id` | Глобальный идентификатор сообщения для дедупликации, UUID v7 | Источник: внутренний пакет или `id` строки outbox при CDC; нет — Outgoing ставит `<узел>:<топик>:<партиция>:<смещение>` (ADR-0024) | Ingoing — дедупликация | ADR-0022, ADR-0024 |
| `x-schema` | Полное имя типа Protobuf (`<package>.<Message>`) | Источник: внутренний пакет; при CDC — колонка outbox (Outbox Event Router) | Потребители; разбор DLQ | ADR-0022, [ADR-0028](../../90_ADR/ADR-0028%20Заголовки%20x-schema,%20x-event-time,%20traceparent%20при%20CDC.md) |
| `x-event-time` | Время события у источника, ISO 8601 UTC с миллисекундами | Источник: внутренний пакет; при CDC — время фиксации транзакции (`source.ts_ms`) через своё SMT, проверить на стенде; запасной путь — колонка outbox `event_time` | Потребители | ADR-0022, ADR-0028 |
| `traceparent` | Контекст трассировки W3C Trace Context | Библиотеки OTel; при CDC — колонка outbox, если СПО её заполнили | Библиотеки OTel | ADR-0022, ADR-0028; исключение из `x-*` (BL-084) |

Значения заголовков — строки UTF-8 (ADR-0022).

## 5. Дедупликация и защита от зацикливания

- **Дедупликация** — по глобальному уникальному идентификатору сообщения. При первом прохождении через узел идентификатор сохраняется в state store, повторные приходы игнорируются. Это защищает от дублей при повторной доставке MirrorMaker или сбоях.
- **Защита от зацикливания** — заголовок `x-visited`. Узел добавляет себя в него перед отправкой другим узлам и не отправляет сообщение узлам, которые в нём уже есть. Каждое сообщение пересылается каждому узлу не более одного раза; повторный приход (например, при транзите через ОКРУГ, [BL-071](../../80_Базис/BL-071%20Ограничение%20РАЙОНА%20касается%20событий%20Kafka,%20транзит%20через%20ОКРУГ%20разрешён.md)) отсекает дедупликация. Outgoing пересылает дальше и сообщения, пришедшие через Ingoing (со слов архитектора, Q-048), — по правилу из раздела 5.1.

### 5.1. Маршрутизация

Решение — [ADR-0027](../../90_ADR/ADR-0027%20Маршрутизация%20межузлового%20обмена%20—%20редакция%20по%20ревью.md).

- **Каналы.** На узле заводятся только те `sync.n.X`, по которым с этого узла нужно передавать; нет топика — узел туда не передаёт. У РАЙОНА — только `sync.<район>.<свой ОКРУГ>`.
- **Правила по типу источника** (по `x-origin`): данные из РАЙОНА — только вверх, свой ОКРУГ и ЦЕНТР ([BL-087](../../80_Базис/BL-087%20Данные%20РАЙОНА%20поднимаются%20вверх,%20справочники%20—%20всем.md)); остальное, включая справочники КНСИ, — всем.
- **`x-targets`** (массив JSON, ставит источник) сужает цели: цели = `x-targets` ∩ разрешённое правилами; нет заголовка — цели по правилам; недостижимый или запрещённый правилами узел из `x-targets` — сообщение в DLQ объекта `name_spo.name_io.dlq` (объект не определить — `pk_shd.node.dlq`), остальным отправка продолжается.
- **Следующий узел.** Цели минус `x-visited`; для каждой цели — прямой канал, если есть, иначе через ОКРУГ, через который цель доступна. Узел пересылает только то, что источник не может доставить сам; на транзитном узле правила применяются заново и дают тот же результат.
- **Конфигурация** — список узлов, их типы, каналы и правила — в настройках Outgoing, задаётся через Ansible.

Примеры:
- событие РАЙОНА р1 ОКРУГА A: р1 → `sync.р1.A`; A оставляет себе и пишет в `sync.A.центр`; чужие ОКРУГА и РАЙОНЫ не получают;
- справочник КНСИ из ЦЕНТРА: ЦЕНТР пишет напрямую во все ОКРУГА; каждый ОКРУГ пересылает только своим РАЙОНАМ; копий между ОКРУГАМИ нет.

## 6. Гарантии доставки, сбои и порядок

Решение — [ADR-0021](../../90_ADR/ADR-0021%20Гарантии%20доставки%20межузлового%20обмена,%20сроки%20хранения%20и%20DLQ.md).

| Участок | Гарантия |
|---|---|
| СПО → внутренний топик | «как минимум один раз» ([ADR-0007](../../90_ADR/ADR-0007%20Публикация%20событий%20СПО%20—%20outbox,%20CDC%20или%20публикатор.md)) |
| Outgoing → `sync.n.X` | «как минимум один раз» |
| MM2: `sync.n.X` узла n → узел X | «как минимум один раз» |
| Ingoing → внутренний топик | «как минимум один раз», дубли межузлового потока отсекает дедупликация; редкий дубль при сбое Ingoing допустим — потребители идемпотентны |

- **Длительное отключение узла.** Сообщения для узла X копятся в `sync.n.X` на узле n и забираются MM2 узла X после подключения. Срок хранения на узле-источнике — предельная автономность ([BL-083](../../80_Базис/BL-083%20Предельная%20автономность%20узла%20—%20месяц.md)) × 3, сейчас 3 месяца; на узле-получателе — 3 дня, MM2 не переносит `retention.ms`. Срок хранения идентификаторов дедупликации — не меньше срока на узле-источнике. Отключение дольше срока хранения — Q-049.
- **Сбойные сообщения.** То, что Outgoing или Ingoing не может обработать, уходит в DLQ `name_spo.name_io.dlq` (на объект), а если объект не определить — в `pk_shd.node.dlq`; поток не останавливается, разбор вручную, оповещение — Q-020.
- **Порядок.** Гарантируется в пределах ключа и канала: Outgoing и Ingoing сохраняют ключ, у `sync.n.X` одинаковое число партиций на обеих сторонах. Между разными путями (напрямую и транзитом через ОКРУГ) порядок не гарантирован — потребители применяют изменения по версии объекта.

## 7. Варианты топологии

### 7.1. Текущая реализация (полносвязная)

Для каждой пары узлов, между которыми есть канал, — отдельный топик; топики заводятся только по нужным каналам (ADR-0027). В кластере узла n:
- до (N‑1) исходящих топиков: `sync.n.a`, `sync.n.b`, …, `sync.n.X` — по каналам;
- до (N‑1) входящих топиков: `sync.a.n`, `sync.b.n`, …, `sync.X.n` — по каналам.

РАЙОН обменивается только со своим ОКРУГОМ ([BL-052](../../80_Базис/BL-052%20РАЙОН%20обменивается%20данными%20только%20со%20своим%20ОКРУГОМ.md)): у РАЙОНА один исходящий и один входящий топик.

**Поток данных:**
1. Приложение узла n пишет событие во внутренний топик.
2. Outgoing на n определяет цели и для каждой пишет сообщение в `sync.n.<следующий узел>` (раздел 5.1).
3. MM2-коннектор на узле X забирает `sync.n.X` из кластера n и пишет в кластер X под тем же именем.
4. Ingoing на X читает `sync.*.X`, отсекает дубли, добавляет X в `x-visited` и при необходимости пишет во внутренний топик; транзит, не нужный X, — в `pk_shd.transit`, откуда его читает Outgoing X.

**Преимущества:**
- чёткое разделение потоков: сообщения для разных узлов идут по разным топикам — проще мониторинг и отладка;
- простая настройка MirrorMaker: один коннектор на каждый узел-источник, один топик на коннектор;
- узел читает только предназначенные ему топики;
- независимость каналов: сбой доставки одному узлу не влияет на остальные.

**Недостатки:**
- число топиков растёт квадратично: `2 × N × (N‑1)` на всю сеть из N узлов;
- на каждом узле — MM2-коннектор на каждое направление приёма.

### 7.2. Альтернативный подход (для справки)

**Один общий топик на узел.** Каждый узел публикует всё в один исходящий топик, другие узлы читают его и фильтруют по целевому узлу или `x-visited`.
- Плюсы: меньше топиков (2×N).
- Минусы: сложнее фильтрация на стороне получателя; каждый узел читает весь поток.

### 7.3. Обоснование выбора

Из заметки архитектора (BL-045, перенесено в ADR-0016, затем в ADR-0027):
- **надёжность:** отказ одного кластера или канала репликации не влияет на обмен между остальными узлами;
- **простая логика:** нет сложной фильтрации на уровне приложения, кроме дедупликации и обновления `x-visited`;
- **управляемость:** каждое направление репликации настраивается и мониторится отдельно;
- **масштабируемость:** число топиков растёт квадратично, но для небольших и средних кластеров (до 10–15 узлов) это не проблема.
